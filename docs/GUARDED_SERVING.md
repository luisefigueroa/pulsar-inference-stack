# Bounded guarded serving

`pulsar guarded` runs a finite serving session with a foreground lease owner.
It is an opt-in path for model trials, separate from ordinary persistent
`pulsar start`. It uses the normal frozen spec, complete prepared snapshots,
confirmed placement, image validation, model mounts and serving observation.
It never acquires weights, pulls an image, replaces a service or qualifies a
model implicitly.

Stage the recipe's exact image before the trial through the public
`pulsar image check|stage` commands. For a local image with a verified tag in
the pinned repository, review `image stage SPEC --spec-file FILE --export-tag
TAG --plan --json`, then apply the same selection with `--yes`. Named exports
verify the source tag and digest, refuse destination tag conflicts, and verify
the exact repository/digest reference after loading. They never pull from a
registry. Image staging and guard execution remain separate actions.

## Author the guard

Obtain the pinned image's entrypoint from image inspection, then generate a
policy through the public API. The example uses a generic Python image entrypoint:

```sh
./pulsar guarded template \
  --entrypoint-json '["python3", "/opt/model/entrypoint.py"]' \
  --min-host-available-bytes 25769803776 \
  --startup-timeout-seconds 7200 --timeout-seconds 10800 --json
```

Place the returned envelope's `result` in the draft's `recipe.container.guard`.
Set an explicit `memory_limit_bytes`, host networking, no restart and null Docker
healthcheck. Freeze the complete draft with its actual snapshot manifest through
`pulsar spec freeze`, then review the new spec ID. No synthetic model manifest
belongs in a physical trial.

| Guard field | Binding |
| --- | --- |
| `schema_version` | 1 (fixed 64 MiB swap allowance) or 2 (explicit allowance) |
| `program_sha256` | Exact guard executable content generated by this Stack |
| `entrypoint` | Exact entrypoint of the pinned image; checked before release |
| `min_host_available_bytes` | Host available-memory stop floor, 8–128 GiB |
| `startup_timeout_seconds` | Rank-0 HTTP health deadline, 10–14400 seconds |
| `timeout_seconds` | Whole-container lifetime, 10–21600 seconds; includes startup |
| `max_host_swap_growth_bytes` | Schema 2 only; required integer from 0 through 268435456 (256 MiB) |

Changing the guard or its limits changes recipe identity. Omitting `guard`
preserves existing schema-2/3 recipe identities and ordinary launch behavior.
Explicit null/unknown fields are rejected. The guard requires a 1–112 GiB
container memory cap. Its version fixes a 30-second lease, 250 ms resource
sampling interval and bounded model logs. Schema 1 retains its fixed 64 MiB
host-swap-growth allowance and unchanged document shape. Select schema 2
explicitly when a different bounded allowance has been reviewed:

```sh
./pulsar guarded template \
  --entrypoint-json '["python3", "/opt/model/entrypoint.py"]' \
  --max-host-swap-growth-bytes 268435456 --json
```

The template defaults to schema 1 when the option is omitted. A schema-2 value
applies independently to every rank, measured as an absolute increase from that
rank's guard startup baseline for the entire session. It never resets or grows
automatically. Equality is allowed; one byte above the selected allowance stops
the workload. Zero is valid and permits no increase. This controls host-wide
swap growth; container swap remains disabled. The host-memory floor, cgroup cap,
OOM checks, lease and deadlines remain independent stop conditions. Model-free
diagnostics retain their existing 64 MiB behavior.

Changing guard code changes its program hash as well as any policy-driven recipe
identity. Preserve historical specs and plans; create a new candidate using the
installed template. Historical plans retain their own executable for observation,
but an old spec cannot silently launch using a different installed guard hash.

```sh
./pulsar guarded validate --spec-file candidate.json --json
./pulsar guarded run --spec-file candidate.json --spec-id SPEC_SHA256 \
  --output-dir NEW_PRIVATE_DIRECTORY \
  --memory-estimate-file weights.json --memory-estimate-id ESTIMATE_SHA256 \
  --yes --json
```

The memory estimate is optional and retains its existing contract. Any memory
warning needs the explicit `--accept-memory-warn` decision. The runner uses the
first N confirmed nodes by default. For a multi-node recipe, pass the ordered
`--placement-nodes NODE_ID,NODE_ID` list to `model prepare`, `model info`,
`image check|stage`, `start --dry-run`, `guarded run` and pre-launch `resources`.
The list must match the recipe's exact node count, contain unique confirmed
nodes, and satisfy its fabric requirement. Its first node runs the API rank.
The complete topology identity and saved membership remain unchanged. A storage
home can remain on another confirmed member; Stack verifies it independently
and requires complete working copies on every participating rank. Existing
pinned views and their bytes are retained. Its output directory must not exist.

Ordinary real start supports its existing default placement; a nondefault
multi-node placement requires the guarded path. Stop that session through
`guarded stop` with its exact run ID. Ordinary stop refuses a recorded
nondefault guarded placement before removing containers. Recorded observation
and service resource sampling use the saved rank/node bindings rather than a
future selection or overlay. A remote API head does not write the controller's
`ready.json`; use public status or observation to inspect readiness.
The command stays active for the lifetime of the session. `--yes` acknowledges
the reviewed start, not acquisition, replacement or publication.

## Enforcement and identity

The normal read-only prerequisites run first through `start --dry-run`.
Ordinary `start` continues to refuse guarded recipes; it does not acquire
foreground ownership implicitly. A schema-6 launch plan retains the exact
guard program and a unique invocation ID. The program's hash must match the
recipe. Observation uses these retained bytes rather than the current checkout,
so a source update does not redefine an already-running service's guard.

Each node starts only a framework-free CPU wrapper in the approved image.
Before releasing the model, Stack verifies image, entrypoint, command, labels,
read-only model mounts and resource bindings. The wrapper itself verifies cgroup
memory and swap controls and obtains a fresh resource sample before release.

Guarded containers use memory-plus-swap equal to the recipe's memory cap, which
disables container swap, a private cgroup namespace, PID limit 512, no restart
and automatic removal. A read-only host meminfo mount supplies physical memory
and swap observations. These derived settings and the wrapper are explicit
guard semantics and are verified by normal serving observation. The original
image entrypoint and engine arguments execute as the wrapper's child.

The effective host floor is the larger of the declared floor and startup
available memory minus the container cap. Startup requires at least the larger
of the cap and declared floor available; it does not reserve their sum. The
host floor can therefore stop growth before the full cgroup cap is reached.
Memory estimation/admission remains necessary.

The CPU guard stops for missing samples, cgroup OOM events, memory limit,
host-memory floor, host-swap growth, time limit, lease loss, interruption or
model exit. It terminates the child process group, then exits the container so
remaining processes in that container namespace cannot continue. The guard
survives loss of the host launcher; renewals cannot revive an expired lease.
Failure of one supervised rank cancels its peers. Cleanup uses the invocation's
ownership labels and immutable container IDs; unrelated containers are preserved.

The memory cap is a cgroup setting and the host floor is sampled enforcement.
This is not a framework-wide CUDA allocator cap or proof that GPU memory spikes
cannot occur between samples. Kernel allocations, load/repacking peaks and
physical fit still require a separately approved hardware trial.

## Observe and stop

`active-plan.json` records the service/run identities before execution. Rank 0
writes `ready.json` after authenticated `/health` succeeds; this is API health,
not output correctness or qualification. Use the ordinary public `status`,
`inventory`, `observe` and resource sampling operations to inspect the service.
The guard uses its own startup deadline instead of the ordinary launcher retry
count. Whole-session time continues through smoke and observation.

```sh
./pulsar guarded stop --output-dir PRIVATE_DIRECTORY --run-id RUN_SHA256 --json
```

Stop verifies the invocation and controller PID/start time, records the request,
then signals that controller. A successful stop request is not cleanup proof:
wait for the foreground run's final `result.json`. It records each phase and
requires every rank's cleanup. Normal model stop also causes the guard to fail
closed, but an explicit guarded stop distinguishes the requested end of a trial.

Rank guard reports include `baseline_sample`, `last_sample`, `trigger_sample`,
`host_swap_growth_limit_bytes`, `max_observed_host_swap_growth_bytes` and
`effective_host_available_floor_bytes`. Samples contain host memory/swap,
cgroup current/peak memory, OOM counters and guard-relative elapsed seconds.
The baseline is the actual startup snapshot; maximum growth is measured against
that fixed snapshot, never the previous sample. `trigger_sample` is null for
stops without a measured guard condition (for example, a disconnected controller),
and `last_sample` may be null if no loop sample was obtained. Missing reports
after cancellation remain missing; these fields do not invent peer evidence.
Retain external resource sampling through cleanup when a complete trace is needed.

Retain incomplete/failed records. If the controller is killed, no final result
is invented: the independent wrappers expire, and subsequent recovery must
verify actual containers and model state through Stack before another start.
There is no implicit resume or retry. A stop or clean exit is not baseline
qualification. Resource and transport tests in CI are synthetic CPU evidence.
